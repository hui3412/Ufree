# UFree account test backend

This backend and the connected frontend are for **hui3412/Ufree only**. The frontend remains at https://hui3412.github.io/Ufree/. The API is https://youfreetest.huien3412.workers.dev. Do not deploy this configuration to spacedivee, youfree.ca, or a production Cloudflare account.

## Apply and deploy in the test Cloudflare account

From the repository root after `npm ci`, using an authenticated Cloudflare CLI:

```sh
npx wrangler d1 migrations apply ufree-test-db --remote
npx wrangler deploy
```

The migration creates account tables alongside existing D1 infrastructure. It does not access, migrate, delete, or rename the browser's existing Local database. Confirm the Wrangler account and `DB` binding match `dff58bbe-1cc3-4850-8a58-4532fc9aed4b` before running. No browser/API token should be committed. Wrangler will use its normal authenticated deployment credentials. There are no application secrets to distribute to the browser.

The supplied Git integration deploy command `npx wrangler deploy` now invokes `backend/prepare-deploy.mjs` through the Wrangler custom build hook. Only inside Workers Builds on main, after verifying the exact test Worker and database IDs, it applies pending additive D1 migrations before deployment. Local development and local dry runs skip remote migration. If the connected build token lacks D1 permission, deployment stops and the manual migration command above remains necessary. Keep preview builds off. The same `DB` binding is declared in Wrangler. Cloudflare deployment logs and dashboard settings require access to the test Cloudflare account; repository checks cannot establish those settings.

`GET /` and `GET /health` are database-free liveness endpoints. They report `database: not-checked` and `release: public-health-v2`. They never establish database readiness. Use the separately authenticated manual diagnostics endpoint below for that purpose.

## CPU and monetary considerations

Password hashing uses the OWASP scrypt profile N=32768, r=8, p=3 with random salts. This is deliberately costly. Verify the test Worker's CPU allowance before enabling signup. The ordinary free Worker CPU allowance may be insufficient; a paid Workers plan and a sufficient per-request CPU limit can be necessary. Do not reduce password hashing strength to fit a plan. No paid plan or billing settings were changed by this commit. Charges are for Worker requests/CPU and D1 storage/operations, not a per-account licence. This repository does not promise a zero-cost deployment.

## Persistence and synchronization

- Guest Local collections use the **unchanged** IndexedDB `whos-free-local` / `app` / `schedules` and localStorage fallback `whos-free-local-schedules`.
- Account records, base revisions, pending edits and conflicts live separately under `ufree-test-account-v1:<user id>` in localStorage. Collection preferences have a separate per-account prefix. Browser quota failures are surfaced; they never clear Local storage. Account copies currently have the browser's localStorage quota and a 10 MB server test quota. Cloud snapshot payloads are limited to 2 MB, 2,000 schedules and 500 classes per schedule. Very large stress datasets should continue using Local view.
- Signup explicitly copies the current Local schedules and collection preferences, requires a selected personal schedule and school, and queues the initial cloud upload. It never moves/removes Local data.
- Login on a new context downloads Account data once. Returning contexts render their own local copy immediately. Safari and Home Screen contexts each sign in and maintain their own local copy.
- Account changes save locally before network access. Server revisions and per-name tombstones reconcile concurrent changes. Conflicting edits are separate schedules. In delete/edit conflicts the original stays deleted and the concurrent edit becomes a conflict copy. Names act as record keys with a `p:` namespace separate from account metadata; even a schedule named `@preferences` remains a schedule. Renames are deletion plus addition.
- Opening/foregrounding checks at most once per minute; manual refresh and reconnect can check immediately. Continuous foreground use adds at most one activity-triggered check per hour so an already signed-in person remains active. No cloud request runs on every UI click. An unchanged revision with no pending edits transfers no schedules. Each check is still a request.
- A write sends at most 50 changed records in one optimistic revision batch, retries version conflicts three times, and keeps remaining edits queued after errors. A lost acknowledgement is reconciled on the next check. There is no claim that two offline contexts are immediately identical.
- Sessions are opaque random 256-bit bearer tokens; only token hashes are stored in D1. Browser session credentials stay in that context's localStorage. Requests omit cookies, which avoids assuming Safari supports third-party cookies between GitHub Pages and workers.dev. CORS allows exactly `https://hui3412.github.io`; authorization is independently checked on every private endpoint. Sessions expire after 30 days. Re-signing in restores access to retained pending account edits.
- Sign-out retains both Local and Account cached data. When the API is reachable it invalidates the current session; when offline, sign-out clears this context's session credentials, but the server token may remain valid until expiry. Password changes can revoke other sessions. Shared/device access to cached data must be considered during a later product review; local cached copies are not encrypted.

## Sharing and abuse controls

Cloud snapshots use random 256-bit identifiers, expire exactly 48 hours after the server creates them, and have no early revoke endpoint. Anyone with a valid code/link can retrieve the fixed snapshot without authentication. Imports preserve independent copies after expiry. The account prompt for guests is dismissible and does not prevent receiving. Username lookup returns only the matched username. Sending requires selected schedules, recipient verification and a final details confirmation. Inbox items are never automatically inserted into a collection. Accept imports a copy; Decline does not. Blocking declines pending incoming deliveries and prevents further deliveries in either direction. Limits: 5 signup attempts/IP/hour, 30 snapshots/account/day, 20 deliveries/sender/day, 100 incoming deliveries/recipient/day, 60 lookups/account/hour and 120 public snapshot requests/IP/hour.

Account search returns at most 10 matching usernames, excluding either-way blocks and never exposing school or schedules (60 searches/account/hour). Follow requests require explicit consent to ongoing sharing. The recipient sees an inbox request and must explicitly follow back before either personal schedule is revealed. Acceptance creates a mutual connection: only the two selected Account personal schedules update automatically. Other shares remain independent snapshots. School, source filenames and unrelated imported fields are excluded from live exports.

Live schedules appear as read-only `@username` entries in Account view. Server-owned `f:` records cannot be uploaded or overwritten by clients. Own `p:` records and Local data remain separate. Changes propagate through server revisions and download on opening/foregrounding, reconnection or manual refresh; this is not background push. Offline copies may differ until synced. Personal schedule selection is managed in Account; renaming a selected schedule queues an optimistic selection update after its data syncs.

Stopping a connection or blocking removes both live records on the next sync and stops future updates. Previously exported/imported copies cannot be erased. Limits are 100 pending/accepted connections per account, 20 outgoing requests/day, 50 incoming requests/day and a 24-hour wait before retrying a declined/cancelled pair. Migration `0002_live_following.sql` installs these features; health reports `following: true` when installed.

## Lossless cloud storage v1

Migration `0003_cloud_compression.sql` adds an internal content-addressed object store. Full schedule JSON and Account preference objects are canonicalized by sorting object keys only, then stored as raw DEFLATE bytes when smaller than UTF-8 JSON. Arrays, all known and unknown fields, Unicode, literal control characters and nulls are preserved. No public share-field filter or compact transport layout is used for private Account storage. This reuses the export system's DEFLATE approach without its optional detail projection or base64 text overhead. Format, decoded length and SHA-256 digest are verified when reading. Large objects use 64,000-byte BLOB chunks below D1 row limits.

Two schedules with exactly equal full JSON contents share a single immutable object, regardless of their account or person-name key. Object key order is ignored for identity; array order, filenames, notes and other actual values are not ignored. Different metadata means different full objects. Every account keeps its own private record and revision. Edits create/reuse a new object and change only that account's reference; deletions remove that reference. Deduplication never grants access to a different account's copy. Internal IDs are not exposed as download capabilities and there is no object-download endpoint. Logical per-account quota is based on decoded bytes, so cross-account reuse does not reveal whether another account owns the same schedule.

Cloud snapshots and inbox deliveries store compressed manifests referring to the same full schedule objects, rather than duplicating schedule JSON. Names remain in the manifest. Snapshot access still expires exactly 48 hours after creation and received copies remain independent. Inbox delivery reads are bounded to ten pending items per batch to bound decompression and database work; later pending items remain available after earlier responses. Authentication, usernames, school, revision counters, expiry times and access-control metadata remain ordinary indexed fields. Compressing small searchable fields or random password/session hashes would add overhead or break their security/query purposes.

Live-follow entries continue to reference only the existing strict personal-schedule privacy projection. This projection is a separate compressed object when it differs from the full private schedule; it never replaces the private data. Atomic trigger propagation and the existing revision protocol remain in use. The frontend API still returns ordinary JSON, so existing Safari/Home Screen clients and all Local persistence keys are unchanged.

New writes use the object store immediately. Old JSON remains readable. A delta sync converts at most five legacy records/items owned by that account; daily maintenance converts at most 100 legacy records and one legacy snapshot and delivery, with a 5 MiB input budget. This is gradual migration, not an immediate full-database rewrite. Compare-and-swap conversion cannot overwrite a simultaneous edit. An unchanged `/revision` request still transfers no schedules and does not run a backfill scan.

Objects are staged before a record can reference them. Large object/chunk insertion is atomic. Twenty-four-hour staging leases protect incomplete overall requests and reuse from garbage-collection races; a failed record upload may leave unreachable staged objects until maintenance. A single recursive reachability deletion retains every object needed by any Account record, live projection, snapshot or delivery, including manifest children. Only unreachable objects outside their staging lease are reclaimed. Shared objects are not erased merely because one user removes their copy. This does not change the inactive-account deletion policy or provider backup retention. D1 page allocation, metadata, revisions, required privacy projections and indexes still consume space. Compression ratios depend on data, and additional storage operations/CPU can cost more even when byte storage falls.

**Rollback:** retain the v1 reader and migration while any `@UF1:` references remain. A blind source revert to a JSON-only Worker would make compressed records unreadable. For a full downgrade, first deploy a compatible reader/converter, materialize *all* record, live, snapshot and delivery references back to JSON with compare-and-swap and verify no references remain, then switch the Worker. Do not drop object tables or restore an older database over newer user changes. The Git backup branch is a source checkpoint, not a database backup.

Validation includes full-field/Unicode round trips, cross-account identity, independent edits/deletions, snapshots/inbox reuse and immutability, legacy conversion, read authorization, corrupted bytes, failed chunk transactions, live privacy, reachability collection and a 2,000-schedule query budget test. These tests use SQLite with the D1 ArrayBuffer binding semantics.

## Request and row-read efficiency

Migration `0004_usage_efficiency.sql` is additive. It initializes decoded-byte quota counters and inbox revisions without changing schedule payloads, then maintains them with triggers. Expiry and pending-inbox indexes avoid scans/sorts during cleanup and inbox reads. Account saves read only changed records for quota adjustments, rather than summing the entire collection. Finished collections skip legacy conversion scans; conversion remains bounded for collections that still contain old data.

Both public status URLs use zero D1 statements, including cold starts and missing/broken bindings. Database diagnostics exist only at `POST /admin/diagnostics`. Set a random 32–256 character `ADMIN_DIAGNOSTICS_TOKEN` using a server-side Cloudflare secret, then supply it as a Bearer token in a deliberate manual request. Never put it in frontend code, source control, a URL, or a routine monitor. The endpoint fails closed when no secret is configured; ordinary account tokens cannot authorize it. Each authorized request checks connectivity and reads the last migration using its primary-key index. No background code calls this endpoint.

The test deployment may receive the compatible health hotfix before migration 0004 can run, because exhausted D1 daily quotas also block migration. The Worker remains compatible with migration 0003: saves retain the former logical-quota calculation until the counter column exists, and inbox clients fall back to their existing behavior. Apply migration 0004 after the allowance resets to activate incremental counters and indexes. Do not skip a failed migration by assuming the database changed. Verify the deployed release independently of the GitHub commit.

An investigation on 2026-10-21 found that the three old public status-route schema queries accounted for about 99.7% of D1 rows read in the inspected 24-hour window. Those queries alone read about 20.59 million rows. This identifies the costly code path, not the identity of its callers. Worker request totals include external probes and cannot be eliminated simply by optimizing SQL. Compression reduces bytes stored; it does not eliminate rows scanned. The new public liveness route never accesses D1, and the detailed public health route never accesses D1 either.

Clients persist successful revision-check freshness across reloads, recheck it after acquiring cross-tab locks, coalesce Inbox requests, and fetch Inbox contents automatically only when the revision response indicates a change. Automatic failed requests back off from 15 seconds to five minutes (at least one minute for HTTP 429); expired sessions stop automatic retries. Manual refresh remains available. Pending edits stay local through failures. Canonical key comparison avoids uploading otherwise identical objects just because JSON property order changed. Local schedule keys and the Local/Account boundary are unchanged.

Optional server diagnostics can be enabled with `REQUEST_METRICS=1` in the test Worker environment. They log only normalized route, method, status, statement count and D1 aggregate rows read/written. They never log SQL, usernames, credentials, share codes, schedule contents, IP addresses or arbitrary URLs. Missing D1 row metadata is reported as unknown, not zero. Diagnostics are disabled by default; logging every public probe can itself generate substantial log volume. No logging, billing or external monitor settings were changed by this optimization.

Remaining intentional costs include authenticated revision checks, actual edits, substring username search, password hashing, and scheduled object reachability cleanup. The health cache is isolate-local rather than a global request limiter. Validate real usage after deployment over a comparable time window; regression tests establish query behavior, not a guaranteed billing reduction.


### Quota recovery and traffic verification

D1 daily row-limit failures are returned as `429`, `code: DAILY_QUOTA_EXHAUSTED`, `retryAt` at the next midnight UTC, and `Retry-After`. The frontend also recognizes Cloudflare's HTML Error 1027 before the Worker runs. It persists a shared pause for cloud requests until reset, retaining local schedules and pending edits. Automatic sync does not schedule quota retry timers. Ordinary transient failures retain exponential backoff. An HTTP 429 alone is not assumed to be a daily quota error.

Routine tests run against in-memory SQLite/D1 adapters and simulated browser fetches. `npm test` never needs the deployed backend. Do not point stress tests or retry-loop tests at workers.dev. Use only a few deliberate public checks for deployment verification. Admin diagnostics are manual only. The historical caller is unconfirmed: retained telemetry returned no matching request records and the test account had no load-balancer monitors or endpoint health checks. No statement that bots, ChatGPT, or real users caused the spike is justified by those facts.

After the daily allowance resets, compare equal short idle and normal-use windows using Worker successful/error request counts and D1 read-query/rows-read counts. Use fictional data if testing account writes. Verify no request is triggered by local viewing, search or selected-time changes. Start with one deliberate opening, one return and one manual refresh, allowing the one-minute reuse window. Separate synthetic deployment checks from normal usage. Logging can identify future traffic only; enabling it cannot reconstruct historical caller information. Do not upgrade billing or delete schedules to conceal the pattern.
